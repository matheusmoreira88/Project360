# Project360

Project360 is an original Xbox 360 emulation project. This repository contains an early foundation and a deliberately small PowerPC interpreter. A prototype loader can map unencrypted XEX2 images using no compression or basic zero-fill compression; encrypted images, LZX compression, and general Xbox 360 game startup are not yet supported.

## Current implementation

- C++20 project with CMake and Visual Studio x64 Debug/Release presets.
- A minimal executable that runs an embedded PowerPC smoke program.
- A 64-bit GPR CPU state and a bounded guest-memory buffer.
- Big-endian instruction fetch and bounded 8-, 16-, 32- and 64-bit guest data access. Multi-byte accesses enforce natural alignment. An opt-in 4 KiB page map translates guest virtual addresses to the bounded backing store and enforces read, write and execute permissions; checked byte/word-pattern fills, byte stores and bounded-memory moves validate mapped ranges before writing, including cross-page ranges with non-contiguous physical backing. `GuestMemory::move` uses a fixed-size scratch buffer and preserves overlap between guest virtual ranges. Flat identity access remains the default for existing CPU tests.
- Implemented instructions: `addi`, `addis`, `mulli`, `addic`/`addic.`, `subfic`, immediate `ori`/`oris`/`xori`/`xoris`/`andi.`/`andis.`, `add`, `addc`, `adde`, `addme`, `addze`, `neg`/`nego`, `subf`, `subfc`, `subfe`, `subfme`, `subfze`, `mullw`/`mullwo`, `mulld`/`mulldo`, `mulhw`, `mulhwu`, `mulhd`, `mulhdu`, `divw`/`divwo`, `divwu`/`divwuo`, `divd`/`divdo`, `divdu`/`divduo`, `tw`/`twi`, `td`/`tdi`, `extsb`, `extsh`, `extsw`, `cntlzw`, `cntlzd`, register logical operations (`and`, `andc`, `eqv`, `nand`, `nor`, `or`, `orc`, `xor`), `slw`, `srw`, `sraw`, `srawi`, `sld`, `srd`, `srad`, `sradi`, `rlwinm`, `cmp`/`cmpl`, `cmpi`/`cmpli`, scalar floating compares `fcmpu`/`fcmpo` for non-NaN operands, D-form and indexed loads/stores for byte, halfword, word and doubleword widths, `lmw`/`stmw`, indexed byte-reversed `lhbrx`, `lwbrx`, `sthbrx`, and `stwbrx`, `b`/`ba`, `bc`/`bca` with supported BO forms, `bclr`, and `bcctr` with supported BO/BH forms. Doubleword support includes `ld`/`ldu`, `std`/`stdu`, `ldx`/`ldux`, and `stdx`/`stdux`; the unsupported `lwa` form is diagnosed. `mullw`, `mulhw`, `mulhwu`, `divw` and `divwu` define their low-word result; the architecturally undefined upper destination bits are deterministically cleared in this interpreter. Undefined divide results use deterministic zero. `cntlzw` counts leading zeros in the low 32 bits; `cntlzd` examines all 64 bits. `srawi` uses an immediate 0–31 bit shift, sign-extends the low-word result and updates XER.CA for discarded one bits. `sld`/`srd` zero the result for shift amounts 64–127; `srad` and `sradi` model arithmetic fill and XER.CA. D-form and indexed update accesses reject invalid base/destination register combinations and update RA only after successful memory access. Arithmetic XO forms support OE and Rc where defined; carry instructions track XER.CA with carry-out/no-borrow semantics.
- The optional PowerPC `stfiwx` indexed instruction stores the raw low 32 bits of an FPR as a big-endian word; it performs no conversion and leaves FPR, CR0 and FPSCR unchanged. Tests also cover its reserved-bit and alignment diagnostics.
- `lwarx` and `stwcx.` execute a load/reserve and conditional word store across concurrent interpreter contexts. GuestMemory read/write locks make the conditional check and store atomic against all other memory writes; 4 KiB backing-page generations invalidate reservations. Xenon scheduling, its full memory model and GPU coherence are not implemented.
- PowerPC `isync`, `sync` (L=0) and `lwsync` (L=1) decode and execute with a conservative sequentially consistent host fence. Reserved fields are rejected. The single-step interpreter fetches from GuestMemory on every step and has no instruction cache; Xenon weak-memory outcomes, `eieio`, MMIO ordering and CPU/GPU barriers are not modeled.
- Cacheless PowerPC operation support includes `dcbst`, `dcbf`, `icbi` and data-prefetch hints `dcbt`/`dcbtst` (TH values 0, 1, 3, 8 and 10); they have no cache state to modify in the current coherent GuestMemory/interpreter model. `dcbz` clears the aligned 128-byte Xenon data-cache block through checked GuestMemory writes, including reservation invalidation. Actual caches, privilege behavior, GPU visibility and prefetch performance remain unmodeled.
- CR operations include `mfcr`, `mtcrf`, `mcrf`, `mcrxr` and the eight bitwise forms; `mfspr`/`mtspr` support XER, LR, CTR, SRR0 and SRR1, with SRR access privileged by the modeled MSR.PR bit. Illegal and privileged instructions enter vector `0x700`; `sc 0` enters the system-call vector `0xC00`, saves the following PC and can return through `rfid`. Hypervisor `sc` level 1 is explicitly unsupported.
- Bounded XEX2 parsing reads module flags, security-block size, image size, Title ID, Media ID, title/base versions, platform, executable type, disc number/count, savegame ID, TLS template metadata, with template bounds validation, entry point, file-format flags, basic-compression block descriptors, image flags and page descriptors, and import-library names, versions, and record addresses. When page descriptors are present, their supported section types restrict guest-page permissions and the entry point must reside on a code page. The loader decodes function/data type, library index and ordinal from PE import records before mapping the image. It accepts unencrypted XEX2 files with no compression or basic data/zero-fill compression, validates Xbox PowerPC big-endian PE32 sections, and maps them with page permissions. Encrypted images and other compression formats are rejected; no decryption is attempted.
- The guest execution wrapper intercepts decoded function-import thunks by guest PC. The dispatcher implements nineteen `xboxkrnl.exe` exports: ordinals 267 (`RtlCharToInteger`), 268 (`RtlCompareMemory`), 269 (`RtlCompareMemoryUlong`), 270 (`RtlCompareString`), 284 (`RtlFillMemory`), 285 (`RtlFillMemoryUlong`), 289 (`RtlInitAnsiString`), 290 (`RtlInitUnicodeString`), 293 (`RtlIntegerToUnicodeString`), 298 (`RtlMoveMemory`), 301 (`RtlNtStatusToDosError`), 307 (`RtlUlongByteSwap`), 309 (`RtlUnicodeStringToInteger`), 318 (`RtlUshortByteSwap`) and 320 (`RtlZeroMemory`), 338 (`KeTlsAlloc`), 339 (`KeTlsFree`), 340 (`KeTlsGetValue`) and 341 (`KeTlsSetValue`). The TLS exports use the configured main-thread slot array and are covered by direct tests; other threads are not yet modeled. `RtlNtStatusToDosError` maps a tested subset of common statuses; unknown values return `ERROR_MR_MID_NOT_FOUND`. The numeric parsers accept NUL-terminated ASCII or counted big-endian UTF-16, while integer output writes counted UTF-16 with capacity checks and explicit status returns. `RtlCompareString` returns a signed byte-ordering result in GPR3, with ASCII-only case folding; the memory compare calls return matching byte counts in GPR3; the string initializers write bounded big-endian descriptors; the byte-swap helpers reverse 32-bit and 16-bit values; `RtlFillMemoryUlong` validates 4-byte alignment and repeats its pattern in guest big-endian order; `RtlMoveMemory` handles overlapping ranges with bounded temporary storage. Direct dispatcher tests cover all nineteen exports; the synthetic XEX fixture exercises thirteen, including `RtlCompareString` through its guest thunk in both ASCII case modes. ASCII parsing and status conversion remain covered only by direct tests. Other kernel exports, data-import resolution, thunk rewriting and real title startup remain unsupported.
- `GuestExecutor::run` executes a loaded image up to a caller-provided instruction budget, continues through modeled guest exceptions, and returns explicit fault or budget-stop diagnostics. `project360 --run-xex <path>` loads supported unencrypted XEX2 images into a 512 MiB guest-memory buffer, builds a minimal main-thread launch context (TLS template and slots, PCR, stack and guard page), dispatches the four bounded KeTls services, and executes at most one million instructions. KTHREAD objects, scheduling and broader startup services are absent, so this remains an experimental bounded run path, not general title startup; reaching the budget is not reported as successful execution.
- `project360 --inspect-xex <path>` prints metadata from a supported XEX2 file while explicitly reporting that the image has not been loaded or executed.
- Unsupported or invalid instruction forms report explicit faults. Arithmetic `record` on `add` updates CR0.
- Dependency-free test executables covering PowerPC behavior, guest page mapping, Xenos PM4 packet framing and malformed GPU streams, plus persistent library storage and corrupt input handling.

The initial Xenos command-stream component decodes big-endian PM4 type-0/1 register packets, type-2 no-ops and type-3 command boundaries. It applies type-0/1 writes and type-3 `SET_CONSTANT`, `SET_CONSTANT2` and `SET_SHADER_CONSTANTS` uploads to a caller-sized register file after validating complete stream coverage and the full write set. PM4 NOP is accepted; unimplemented type-3 commands and predicated uploads fail explicitly because draw/bin state is not modeled. Draw execution, other Xenos register semantics, shader translation and Vulkan rendering remain unimplemented.

This is not yet a complete PowerPC or Xenon implementation. Guest exception delivery covers illegal/privileged instructions, integer trap program exceptions and the base `sc 0` path; instruction/data alignment and access failures remain host-side diagnostics, and other exception classes, Xenon-specific MSR behavior, floating-point arithmetic and general FPSCR exception control, VMX128, Xenon thread scheduling and PowerPC memory-ordering semantics, Xbox 360 MMU behavior, broad kernel service dispatch, general XEX image loading, GPU, audio and input remain unsupported. Scalar FPR memory transfers (`lfs`, `lfd`, `stfs`, `stfd`), bitwise move/sign operations (`fmr`, `fneg`, `fabs`, `fnabs`), and non-NaN `fcmpu`/`fcmpo` compares have initial support; unordered quiet-NaN `fcmpu` is covered, while NaN exception cases fault explicitly. The floating-point unit remains incomplete. The page map is a generic prototype, not a reproduction of Xenon translation or its 512 MB unified memory. The desktop frontend is an early scaffold described below. The bounded XEX run command does not establish commercial-game compatibility.

## Desktop interface (early scaffold)

A separate Qt 6 Widgets desktop target provides a Steam-inspired library shell with a local `.xex` file picker, persistent paths, search, name sorting, and removal from the library. It never deletes the original file, parses executable metadata, or runs the XEX. The **Iniciar** action is intentionally disabled until the loader and required runtime subsystems exist. Qt 6.5 or newer with the Widgets module is needed to build this optional target. If Qt is not found, CMake still configures the core, smoke executable, and tests.

## Build and run on Windows

Install CMake 3.24 or newer and Visual Studio 2026 with the x64 C++ toolchain, then from this directory run:

```powershell
cmake --preset windows-debug
cmake --build --preset debug
ctest --preset debug
.
out\build\windows-debug\Debug\project360.exe
```

The smoke program should report `r3=7 r4=12 r5=19`. The test target uses a small built-in harness and requires no downloaded test framework. Toolchain availability and these commands must be verified on the target machine before claiming a successful build.

When Qt is installed and discoverable by CMake, the GUI target is `project360_gui`:

```powershell
cmake --build --preset debug --target project360_gui
```

See [docs/frontend.md](docs/frontend.md) for the current interface scope and build note.
