# Xenos shader work

## Compatibility priority

Graphics validation follows authorized homebrew, then simple 3D, more complex 3D, and an optional lightweight 2D regression target. 2D is not a prerequisite for shader or renderer work.

## Current implementation

The GPU frontend already has bounded PM4 parsing, draw/index preparation, vertex-buffer descriptor decoding and VFETCH attribute conversion. It decodes six-dword texture fetch constants, including dimensions, format and mip/sampling metadata, while retaining all raw words. A bounded storage-layout table recognizes common uncompressed formats plus DXT1/3/5, DXN and CTX1 block sizes. The texture-memory module connects supported decoded fetch descriptors to base-level reads for non-stacked tiled 2D textures: texel coordinates are converted to storage blocks, fetch pitch units (32 pixels) are converted to block pitch, and the pitch is rounded to 32 blocks before address calculation. The descriptor path applies all four Xenos endian modes as byte-lane permutations over aligned physical groups, including neighboring lanes when a format's storage block is smaller than the endian group. A separate block decoder now converts Xenos 8:8:8:8 format 6 and DXT1 format 18 blocks to row-major RGBA8, including the DXT1 transparent selector mode. Tests cover channel masks, RGB565 endpoints/interpolation, transparent texels, malformed block sizes, unsupported formats, descriptor-backed reads, every endian mode, and tiled address periods. Numeric sign/gamma interpretation, fetch swizzle, linear surfaces, mip placement, cube/3D/stacked addressing and shader sampling remain unsupported. Format behavior is cross-checked against the public [Xenia Xenos declarations](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/xenos.h), [texture extent calculation](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/texture_extent.cc), [texture format information](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/texture_info.h) and [texture dump channel masks and DXT FourCC mapping](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/texture_dump.cc); these are behavior references only, and no implementation code was copied. The new `shader_alu` module decodes the three numeric dwords of one Xenos ALU instruction into typed fields: vector/scalar destinations and masks, opcode values, source registers/selectors/swizzles, clamp, export, predicate and constant-address flags.

The decoder preserves opcode values without claiming they are implemented. A bounded source resolver reads one of 64 temporary registers and applies the encoded relative component swizzle plus absolute-value and negate modifiers. Absolute-addressed float constants use a caller-supplied bounded constant bank; a0/aL-relative constants and loop-relative temporaries fail explicitly. The standalone CPU vector evaluator supports ADD (0), MUL (1), MAX (2), MIN (3), SEQ (4), SGT (5), SGE (6), SNE (7), FRC (8), TRUNC (9), FLOOR (10), CNDE (12), CNDGE (13), CNDGT (14), DP4 (15), DP3 (16) and DP2ADD (17); comparisons return per-lane 1.0/0.0 and tests include NaN cases. FRC/TRUNC/FLOOR compute `x - floor(x)`, truncation toward zero and floor toward negative infinity. CNDE/CNDGE/CNDGT choose component-wise between `src2` and `src3` using `src1 == 0`, `src1 >= 0` and `src1 > 0` respectively. MAX and MIN follow the documented compare-select rules for ordered inputs, including deterministic signed-zero tie selection; lanes with NaN operands fail explicitly because Xenos-specific unordered behavior is not yet verified. DP3 and DP4 use separate single-precision products and replicate the scalar sum to each enabled destination lane; their products use the legacy zero/subnormal rule, and DP3 ignores W. DP2ADD computes `src1.x * src2.x + src1.y * src2.y + src3.x`, replicating it to enabled lanes and resolving `src3` through the same temporary/constant source path. Vector `MULADD` (11) remains unsupported while its FMA precision is unresolved: the microcode reference includes both a single-round hardware-accurate FMA note and a general note that multiply-add appears unfused. The current DP4 reference follows the documented XYZW sum order. Xenia records that an IPR sequencer document instead lists WXYZ for DP4, so hardware-level accumulation order remains an explicit differential-validation gap. MUL and paired scalar MULS return positive zero if either operand is zero or subnormal, following the documented Direct3D 9 legacy multiply rule. The paired instruction evaluator supports vector ADD/MUL/MAX/MIN/SEQ/SGT/SGE/SNE/DP4/DP3/DP2ADD with scalar ADDS (0), ADDS_PREV (1), MULS (2), MULS_PREV (3), MULS_PREV2 (4), MAXS (5), MINS (6), SEQS (7), SGTS (8), SGES (9) and SNES (10), FRCS (11), TRUNCS (12) and FLOORS (13), RCPC (17) and RCPF (18). Binary scalar operations take `a`/`b` from the W/X components of `src3`; comparisons consume W only, and previous-result operations consume the incoming scalar `ps`. MULS_PREV2 returns `-FLT_MAX` for its sentinel/non-finite previous value or non-finite/non-positive `src3.x`; otherwise it applies the legacy multiply to `src3.w * ps`. MAXS/MINS follow their documented compare-select expressions, including their resulting unordered selection behavior. RCPC/RCPF currently use host division with the documented infinity clamps; broader reciprocal precision has not been validated. IEEE RCP (19) remains unsupported until its Xenos approximation can be matched. Both halves read the original register bank, scalar `ps` updates even with an empty destination mask, and masked writes commit together. Vertex-shader exports for interpolators 0..15 and position 62 now preserve previously written lanes, track their write masks, and are returned by the ordered EXEC runner. Tests cover full position export, partial interpolator writes and rejection of unimplemented export register 63. This remains an ALU subset: relative constants, loop state, other scalar/vector operations, full control-flow scheduling, GPU memory, SPIR-V translation, draw submission and pixels are outside its scope. Predication, relative destinations, exports outside the documented vertex outputs, clamp and unsupported opcode pairs return explicit errors.

The field map, MAX/MIN compare-select expressions, DP3/DP4/DP2ADD, FRC/TRUNC/FLOOR opcode formulas and legacy multiplication rules for dot operations were checked against the pinned public [Xenia Xenos microcode declarations](https://github.com/xenia-project/xenia/blob/95a5c3ee250f80c3b9d139658649d9ffb6db3eec/src/xenia/gpu/ucode.h). This is a format reference only; Project360 does not copy its implementation. Xenia's GPU notes identify the XNA Game Studio 3.1 Xbox 360 shader assembler as a primary encoding/validation reference; no XNA binary or proprietary content is included here. Since that source does not settle Xbox-specific NaN behavior for MAX/MIN, Project360 rejects those unordered lanes pending validation.

## Straight-line EXEC reference path

The PM4 draw-stream reader now handles unpredicated `IM_LOAD` (`0x27`) and `IM_LOAD_IMMEDIATE` (`0x2B`) packets. Pointer loads read guest physical memory after converting the GPU address; immediate loads consume the packet's inline big-endian dwords. Both paths validate the shader stage, require a nonempty size made of complete three-dword microcode records, and reject unsupported nonzero start offsets. A successfully loaded vertex or pixel program is retained as an immutable active shader and captured by each later prepared draw, so subsequent loads do not rewrite prior draw snapshots. Tests use self-authored synthetic records, pass the captured vertex records into the explicit-prefix EXEC decoder, and run that bounded CPU reference sequence. This connects PM4 packet parsing to shader capture and the existing reference executor; it does not infer a control-flow prefix automatically, translate shaders to SPIR-V, execute pixel shaders in Vulkan, or establish title compatibility. Packet layouts are cross-checked against the public [Xenia command processor](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/command_processor.cc), [Xenos address conversion](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/xenos.h) and [microcode declarations](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/ucode.h), used as format references only.

The same stream processor now tracks the 64-bit PM4 bin mask and bin selection through `SET_BIN_MASK`/`SET_BIN_SELECT` and their low/high updates. Predicated type-3 packets are skipped when the current selected-bin intersection is zero; a selected packet continues through its normal validation and processing path. Tests cover both full-width and split-register updates, skipped shader loads, and selected malformed loads failing transactionally. This models packet selection only; tiled rendering, bin-dependent resource state and swap/presentation remain unsupported. The opcode values and predicate behavior were checked against the public [Xenia Xenos declarations](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/xenos.h) and [command processor](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/command_processor.cc), used as behavior references only.

`LOAD_ALU_CONSTANT` (`0x2F`) copies a bounded range of big-endian dwords from guest physical memory into the selected register bank in PM4 order. Supported types are ALU, fetch, boolean, loop and direct registers. The frontend validates packet shape, bank type, nonzero dword count, guest-memory bounds and destination register bounds before committing the range. Synthetic tests check all five bank mappings and load a float4 into distinct per-draw snapshots; out-of-range memory and unsupported types fail without exposing partial state. The optional Vulkan smoke fixture also uses this packet to populate c7 from guest physical memory, decodes it from the draw snapshot, passes it through the CPU shader reference execution and rasterizes the first vertex batch. A second synthetic draw reloads c7 with X=0.125 and verifies the CPU vertex result changes its first position X by 0.125. Other memory-backed constant commands remain unsupported. The address mask, type/index fields and dword size follow the public [Xenia command processor](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/command_processor.cc), used as a format reference only.

`shader_execution` decodes `EXEC`, `EXEC_END`, `COND_EXEC` and `COND_EXEC_END` headers, then reads the two-bit-per-instruction sequence to choose ALU or fetch execution. `decode_shader_exec_pairs` unpacks both 64-bit control-flow headers from each packed three-dword record; literal-field and input-bound tests cover this format step. `decode_shader_exec_program` now parses an explicitly sized control-flow prefix from a complete array of three-dword records and validates every supported EXEC block range against that same array. EXEC instruction addresses remain absolute record indexes, so the original unrebased microcode array can be passed directly to the CPU runner. Prefix length remains explicit; the decoder does not guess it from contents. The record packing and address indexing were cross-checked against the public [Xenia control-flow and shader translator declarations](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/ucode.h) and [shader translator](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/shader_translator.cc), used as format references only. Its synchronous CPU reference path commits supported ALU pairs and full VFETCH operations in sequence order. `execute_shader_exec_sequence` runs a bounded linear list of blocks, preserving temporary registers, scalar previous-result and vertex exports between blocks. Conditional blocks can skip their slots and a matching conditional end can terminate execution; an unterminated sequence fails without exposing partial state. Branches, calls, loops and predicate flow are not modeled. `execute_shader_exec_vertex_batch` runs this sequence independently for each prepared vertex index, seeds `r0.x` with the remapped 24-bit index, and returns all outputs or none on failure. The startup convention is cross-checked against the pinned public [Xenia DXBC shader translator](https://github.com/xenia-project/xenia/blob/95a5c3ee250f80c3b9d139658649d9ffb6db3eec/src/xenia/gpu/dxbc_shader_translator.cc); no implementation code is copied. A bounded `process_pm4_draw_stream` path applies supported PM4 register writes and DMA/auto-index draw packets in packet order, then prepares each draw against the register state at that point and retains a bounded per-draw register snapshot (32 MiB aggregate limit). Requested VFETCH slots can be decoded from the two-dword vertex-descriptor layout in the resulting register file; requested ALU float4 constants are decoded from four IEEE-754 register dwords each, starting at `0x4000`. Texture descriptors use a separate six-dword layout; requested entries expose bounded dimensions, format, base and mip addresses, component swizzle, filters and signed LOD metadata, while guest texture reads and sampling remain unsupported. This is limited to the 96 vertex-fetch slots documented in the public [Xenia Xenos format declarations](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/xenos.h). Unsupported commands fail transactionally. `execute_pm4_draw_vertex_batch` connects a prepared PM4 draw to the CPU shader reference path by evaluating supported bool-constant conditions, collecting referenced VFETCH slots and ALU constants only from active blocks, resolving them from the draw's retained snapshot, and executing the prepared indexes. The Vulkan hardware smoke test exercises this helper with a synthetic PM4 `DRAW_INDX` and runs two shader blocks per resulting vertex: two VFETCH operations read position/color from an interleaved guest buffer, one ALU vector ADD consumes PM4-loaded c7, then paired ALU operations export position and interpolator 0. It prepares triangle indices from a physical DMA buffer via `prepare_draw_geometry`, passes batch outputs and geometry into `render_offscreen_xenos_geometry`, and verifies rasterized readback. Malformed ranges, missing constants, relative addresses, out-of-range vertex indexes, missing shader termination and unsupported instructions fail explicitly; any failed block discards the whole vertex batch. This remains a straight-line block sequence: general PM4 command/state dispatch, branches/calls/loops, texture sampling, exports outside the implemented vertex outputs, relative constants, viewport behavior outside the bounded clipped X/Y subset, translated SPIR-V and a game frame remain unsupported.

The PM4/Vulkan smoke fixture now writes `PA_SC_SCREEN_SCISSOR_TL/BR` and `PA_SC_WINDOW_SCISSOR_TL/BR`. `read_xenos_scissor_rectangle` decodes the signed screen bounds and unsigned window bounds, applies the optional signed window offset, intersects the rectangles and clips the result to the target. The synthetic draw passes its resolved 8×16 scissor into Vulkan dynamic state; pixel readback checks that only the left half can contain the triangle. This validates scissor application in the bounded smoke path, not the complete Xenos rasterizer. Register positions and field layouts were cross-checked against the public [Xenia register table](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/register_table.inc) and [register declarations](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/registers.h); these are format references only, and no implementation code was copied.

`read_xenos_viewport` adds a bounded clipping-enabled X/Y/Z mapping for `PA_CL_VPORT_*`, `PA_CL_VTE_CNTL`, `PA_CL_CLIP_CNTL`, `PA_SU_SC_MODE_CNTL` and `PA_SU_VTX_CNTL`. It resolves enabled X/Y scales and offsets, the optional signed vertex window offset and the D3D half-pixel shift into a positive Vulkan viewport; negative X/Y scales are represented by reflecting the clip-space axis before rasterization. Enabled Z scale/offset values become a clamped Vulkan depth range. For Xenos symmetric `-W..W` depth clipping, the Vulkan adapter maps Z to `0..W` using `0.5*Z + 0.5*W`; reverse depth ranges are canonicalized and reflected in clip space. Tests cover D3D and symmetric clipping, offset/scale, reverse Z, non-finite values and unsupported modes. Clipping-disabled draws and user clip planes fail explicitly. The viewport math follows the public [Xenia draw utility](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/draw_util.cc), used only as a behavior reference; no implementation code was copied. This partial map still lacks full clipping/viewport behavior and is not evidence of a rendered Xenos game frame.

## Next 3D milestones

1. Expand the ALU operations against documented encodings, keeping scalar and vector semantics explicit.
2. Extend the sequence runner with conditional control flow, predicates, and loop behavior only as each state transition is validated.
3. Extend PM4-decoded raster state beyond the bounded clipped X/Y viewport and window/screen scissor paths, then model the remaining Xenos clipping and viewport cases against validated references.
4. Translate guest vertex/pixel shaders to SPIR-V and validate them differentially against the CPU reference before broader Vulkan submission.
5. Test with an authorized simple 3D homebrew/title only when its startup and rendering dependencies are known.

No 3D title or rendered Xenos frame has been confirmed yet.
