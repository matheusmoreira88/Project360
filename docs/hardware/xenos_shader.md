# Xenos shader work

## Compatibility priority

Graphics validation follows authorized homebrew, then simple 3D, more complex 3D, and an optional lightweight 2D regression target. 2D is not a prerequisite for shader or renderer work.

## Current implementation

The GPU frontend already has bounded PM4 parsing, draw/index preparation, vertex-buffer descriptor decoding and VFETCH attribute conversion. The new `shader_alu` module decodes the three numeric dwords of one Xenos ALU instruction into typed fields: vector/scalar destinations and masks, opcode values, source registers/selectors/swizzles, clamp, export, predicate and constant-address flags.

The decoder preserves opcode values without claiming they are implemented. A bounded source resolver reads one of 64 temporary registers and applies the encoded relative component swizzle plus absolute-value and negate modifiers. Absolute-addressed float constants use a caller-supplied bounded constant bank; a0/aL-relative constants and loop-relative temporaries fail explicitly. The standalone CPU vector evaluator supports ADD (0), MUL (1), MAX (2), MIN (3), SEQ (4), SGT (5), SGE (6), SNE (7), FRC (8), TRUNC (9), FLOOR (10), CNDE (12), CNDGE (13), CNDGT (14), DP4 (15), DP3 (16) and DP2ADD (17); comparisons return per-lane 1.0/0.0 and tests include NaN cases. FRC/TRUNC/FLOOR compute `x - floor(x)`, truncation toward zero and floor toward negative infinity. CNDE/CNDGE/CNDGT choose component-wise between `src2` and `src3` using `src1 == 0`, `src1 >= 0` and `src1 > 0` respectively. MAX and MIN follow the documented compare-select rules for ordered inputs, including deterministic signed-zero tie selection; lanes with NaN operands fail explicitly because Xenos-specific unordered behavior is not yet verified. DP3 and DP4 use separate single-precision products and replicate the scalar sum to each enabled destination lane; their products use the legacy zero/subnormal rule, and DP3 ignores W. DP2ADD computes `src1.x * src2.x + src1.y * src2.y + src3.x`, replicating it to enabled lanes and resolving `src3` through the same temporary/constant source path. Vector `MULADD` (11) remains unsupported while its FMA precision is unresolved: the microcode reference includes both a single-round hardware-accurate FMA note and a general note that multiply-add appears unfused. The current DP4 reference follows the documented XYZW sum order. Xenia records that an IPR sequencer document instead lists WXYZ for DP4, so hardware-level accumulation order remains an explicit differential-validation gap. MUL and paired scalar MULS return positive zero if either operand is zero or subnormal, following the documented Direct3D 9 legacy multiply rule. The paired instruction evaluator supports vector ADD/MUL/MAX/MIN/SEQ/SGT/SGE/SNE/DP4/DP3/DP2ADD with scalar ADDS (0), ADDS_PREV (1), MULS (2), MULS_PREV (3), MULS_PREV2 (4), MAXS (5), MINS (6), SEQS (7), SGTS (8), SGES (9) and SNES (10), FRCS (11), TRUNCS (12) and FLOORS (13), RCPC (17) and RCPF (18). Binary scalar operations take `a`/`b` from the W/X components of `src3`; comparisons consume W only, and previous-result operations consume the incoming scalar `ps`. MULS_PREV2 returns `-FLT_MAX` for its sentinel/non-finite previous value or non-finite/non-positive `src3.x`; otherwise it applies the legacy multiply to `src3.w * ps`. MAXS/MINS follow their documented compare-select expressions, including their resulting unordered selection behavior. RCPC/RCPF currently use host division with the documented infinity clamps; broader reciprocal precision has not been validated. IEEE RCP (19) remains unsupported until its Xenos approximation can be matched. Both halves read the original register bank, scalar `ps` updates even with an empty destination mask, and masked writes commit together. Vertex-shader exports for interpolators 0..15 and position 62 now preserve previously written lanes, track their write masks, and are returned by the ordered EXEC runner. Tests cover full position export, partial interpolator writes and rejection of unimplemented export register 63. This remains an ALU subset: relative constants, loop state, other scalar/vector operations, full control-flow scheduling, GPU memory, SPIR-V translation, draw submission and pixels are outside its scope. Predication, relative destinations, exports outside the documented vertex outputs, clamp and unsupported opcode pairs return explicit errors.

The field map, MAX/MIN compare-select expressions, DP3/DP4/DP2ADD, FRC/TRUNC/FLOOR opcode formulas and legacy multiplication rules for dot operations were checked against the pinned public [Xenia Xenos microcode declarations](https://github.com/xenia-project/xenia/blob/95a5c3ee250f80c3b9d139658649d9ffb6db3eec/src/xenia/gpu/ucode.h). This is a format reference only; Project360 does not copy its implementation. Xenia's GPU notes identify the XNA Game Studio 3.1 Xbox 360 shader assembler as a primary encoding/validation reference; no XNA binary or proprietary content is included here. Since that source does not settle Xbox-specific NaN behavior for MAX/MIN, Project360 rejects those unordered lanes pending validation.

## Straight-line EXEC reference path

`shader_execution` decodes `EXEC`, `EXEC_END`, `COND_EXEC` and `COND_EXEC_END` headers, then reads the two-bit-per-instruction sequence to choose ALU or fetch execution. Its synchronous CPU reference path commits supported ALU pairs and full VFETCH operations in sequence order to one temporary-register bank and vertex-output state. Boolean conditionals read a caller-provided bool-constant bank and require absolute instruction addressing; a nonmatching block executes no slots, and `COND_EXEC_END` ends the shader only when its condition matches. Synthetic programs verify ALU-produced vertex-index input, a memory-backed VFETCH result, a following ALU result, and propagation of an ALU position export; conditional tests cover matching and skipped blocks plus conditional termination. `execute_shader_exec_vertex_batch` runs one shader-ending block for each prepared vertex index, writes the remapped 24-bit index to `r0.x`, and returns all vertex outputs or no outputs on any failure. This startup convention is cross-checked against the pinned public [Xenia DXBC shader translator](https://github.com/xenia-project/xenia/blob/95a5c3ee250f80c3b9d139658649d9ffb6db3eec/src/xenia/gpu/dxbc_shader_translator.cc); no implementation code is copied. The Vulkan hardware smoke test now executes a four-slot synthetic block per vertex: two VFETCH operations read position/color from an interleaved guest buffer, then paired ALU exports write position and interpolator 0. It prepares triangle indices from a physical DMA buffer via `prepare_draw_geometry`, passes batch outputs and geometry into `render_offscreen_xenos_geometry`, and verifies rasterized readback. Malformed ranges, missing constants, relative addresses, out-of-range vertex indexes and unsupported instructions fail explicitly; a VFETCH failure in any batch item discards earlier output. This remains one shader-ending EXEC block, not a full shader program: PM4 draw dispatch, preceding EXEC blocks, predicate/loop control flow, texture fetch, exports outside the implemented vertex outputs, relative constants, viewport/clipping, translated SPIR-V, and a game frame remain unsupported.

## Next 3D milestones

1. Expand the ALU operations against documented encodings, keeping scalar and vector semantics explicit.
2. Extend the sequence runner with conditional control flow, predicates, and loop behavior only as each state transition is validated.
3. Feed PM4-decoded command state into the prepared-geometry-to-Vulkan path, then model Xenos clipping and viewport conversion against validated references.
4. Translate guest vertex/pixel shaders to SPIR-V and validate them differentially against the CPU reference before broader Vulkan submission.
5. Test with an authorized simple 3D homebrew/title only when its startup and rendering dependencies are known.

No 3D title or rendered Xenos frame has been confirmed yet.
