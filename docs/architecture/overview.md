# Initial architecture

The first build has three small layers:

- `memory::GuestMemory` owns a bounded byte buffer and exposes big-endian 8-, 16-, 32- and 64-bit accesses. Multi-byte accesses enforce natural alignment in this prototype. It is a test memory model, not the Xbox 360 virtual memory system.
- `cpu::decode` converts a 32-bit PowerPC instruction word into a typed operation or an explicit diagnostic.
- `cpu::Interpreter` executes one instruction or a bounded sequence against `CpuState` and guest memory. Current compare instructions update the selected CR field; conditional branches use CR bits and CTR according to their BO/BI fields. Unsupported or reserved forms return a fault instead of silently succeeding.

`CpuState` includes 32 FPR bit containers and an FPSCR storage field. Scalar `lfs`, `lfd`, `stfs`, and `stfd` transfers work in D and indexed forms, including update variants. `lfs` widens an IEEE binary32 value into the binary64 FPR representation; `stfs` converts back to binary32. Indexed `stfiwx` stores the low 32 bits of an FPR unchanged as a big-endian word; it does not convert the value or modify CR0/FPSCR. Bitwise unary `fmr`, `fneg`, `fabs` and `fnabs` preserve payload bits; their record forms copy FPSCR summary bits to CR1. Floating arithmetic, general FPSCR writes/exception behavior, denormal exception behavior and VMX128 are not implemented, so these transfers and unary operations do not support floating-point programs generally. Opcode assignments and `fmr` field semantics were checked against IBM's [PowerPC instruction reference](https://www.ibm.com/docs/en/aix/7.1.0?topic=reference-appendix-f-powerpc-instructions), [fmr reference](https://www.ibm.com/docs/en/aix/7.2.0?topic=set-fmr-floating-move-register-instruction) and [stfiwx reference](https://www.ibm.com/docs/en/aix/7.1.0?topic=is-stfiwx-store-floating-point-as-integer-word-indexed).

## Memory mapping prototype

`GuestMemory` retains a bounded byte buffer as physical backing storage. Page mapping is opt-in, uses a fixed 4 KiB page size in this prototype, supports aliases, and checks read/write/execute access separately. CPU instruction fetch now requests execute permission, while data operations request read or write permission. `load()` is a host-side initialization path to populate backing bytes. This is generic virtual-to-physical translation only: it has no Xenon segment/page-table rules, MMIO, shared CPU/GPU coherence, concurrent access synchronization, demand paging, or 512 MB console memory model.

`lwarx` and `stwcx.` provide a sequential reservation path for a single interpreter context. GuestMemory tracks write generations per 4 KiB physical backing page, so writes through typed, byte-range, fill, move, loader and aliased mappings invalidate a reservation on that page. At 512 MiB of backing memory, the generation table adds 1 MiB of host memory. A conditional store must also target the same physical word; CR0 records success and XER.SO. The 4 KiB reservation granule is an explicit prototype choice, not a measured Xenon granule. There is no concurrent guest-thread scheduler or thread-safe memory access yet, so these instructions do not establish multicore Xenon synchronization. Instruction semantics were checked against IBM's [`lwarx`](https://www.ibm.com/docs/en/aix/7.2.0?topic=set-lwarx-load-word-reserve-indexed-instruction) and [`stwcx.`](https://www.ibm.com/docs/en/aix/7.1.0?topic=set-stwcx-store-word-conditional-indexed-instruction) references.

## XEX2 metadata parser

`loader::parse_xex2` validates the fixed XEX2 header, optional-header directory, security-info bounds, page-descriptor count, file-format information, and the Import Libraries optional header. It extracts bounded library names, versions, and import-record addresses. During load, the record words in PE headers/sections are decoded and checked for a valid image address, matching library index, and supported type. `parse_xex2_file` reads only the declared bounded header, while `load_xex2_file` applies a 512 MiB file-size cap. The loader supports only encryption type 0 and compression type 0. It validates the Xbox PowerPC big-endian PE32 machine/subsystem, image bounds, section ranges, header overlap and section overlap, then transactionally maps pages and copies PE headers/sections into guest memory with read/write/execute permissions. `kernel::GuestExecutor` indexes decoded function-thunk addresses and intercepts calls at their guest PCs; the currently supported shims are `xboxkrnl.exe` ordinals 268 (`RtlCompareMemory`), 269 (`RtlCompareMemoryUlong`), 284 (`RtlFillMemory`), 285 (`RtlFillMemoryUlong`), 289 (`RtlInitAnsiString`), 290 (`RtlInitUnicodeString`), 298 (`RtlMoveMemory`), 307 (`RtlUlongByteSwap`), 318 (`RtlUshortByteSwap`) and 320 (`RtlZeroMemory`). Both compare shims return matched byte counts in GPR3; the string initializers read NUL-terminated source strings, enforce counted-string size limits and write 8-byte big-endian descriptors with transactional guest byte stores. Unicode string lengths are measured in bytes and remain even. The byte-swap shims reverse 32-bit and 16-bit values and return them zero-extended in GPR3. Fill and move services modify validated guest ranges and return through LR. A synthetic XEX caller exercises all ten shims, checks comparison results, copied bytes, both string descriptors and byte-swap results, then resumes guest code. Data-import resolution, general thunk rewriting, relocation and most kernel services remain unsupported. This is not yet commercial game startup. XEX import ordinals are cross-checked against the public [XboxDev xboxkrnl.h export list](https://github.com/XboxDev/xbedump/blob/master/xboxkrnl.h) and [RXDK-Libs](https://github.com/Team-Resurgent/RXDK-Libs/blob/main/libs/libkernel/xboxkrnl.def). String initializer semantics and field layouts are checked against [Microsoft's RtlInitAnsiString](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-rtlinitansistring), [RtlInitUnicodeString](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-rtlinitunicodestring), [ANSI_STRING](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-string) and [UNICODE_STRING](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_unicode_string) documentation. Byte reversal is cross-checked against [Microsoft's RtlUlongByteSwap](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-rtlulongbyteswap) and [RtlUshortByteSwap](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-rtlushortbyteswap) references. The compare behaviors are checked against [Microsoft's RtlCompareMemory](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-rtlcomparememory) and [RtlCompareMemoryUlong](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-rtlcomparememoryulong) documentation. The `RtlFillMemoryUlong` contract is checked against [Microsoft's DDI documentation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-rtlfillmemoryulong), and overlap behavior for `RtlMoveMemory` against [Microsoft's DDI documentation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-rtlmovememory). The format fields and machine/subsystem checks are cross-checked against the public [Xenia XEX definitions](https://github.com/xenia-project/xenia/blob/master/src/xenia/kernel/util/xex2_info.h) and [PE validation flow](https://github.com/xenia-project/xenia/blob/master/src/xenia/cpu/xex_module.cc).

`project360_core` contains reusable emulator code, `project360` is the smoke-program executable, and `project360_tests` is a standalone CTest target. Frontends, guest loaders and platform graphics/audio APIs are intentionally not dependencies of the CPU core.

## Program exceptions and fault reporting

`StepResult` attaches an `ExecutionFault` to interpreter faults. The record classifies illegal and privileged instructions, instruction alignment/access faults, data alignment/access faults, unsupported instructions, and internal consistency errors; it includes the faulting PC, fetched word when available, and effective address when applicable. Illegal and privileged instructions enter the PowerPC program exception vector at `0x700`, save SRR0/SRR1, and report a `GuestException`. `sc 0` saves CIA+4 to SRR0, saves the architecturally selected MSR bits in SRR1, and enters vector `0xC00`; `rfid` can return to the next guest instruction. Reserved SC fields are rejected, and `sc` LEV=1 returns an unsupported-instruction diagnostic without changing guest state. The current implementation handles illegal/privileged program syndromes, and `rfid` restores a subset of MSR state. SRR0/SRR1 `mfspr`/`mtspr` transfers are restricted when modeled MSR.PR is set.

This is a narrow PowerPC exception subset, not the Xenon exception system: data/instruction access and alignment faults remain host diagnostics, and other exception classes, full MSR behavior, hypervisor/LPES configuration and interrupt delivery are not implemented. The `sc` encoding and CIA+4/SRR/vector behavior follow the public [PowerPC User ISA, Book I v2.02](https://powerpc.dev/general/PPC_Vers202_Book1_public.pdf) and [Operating Environment Architecture, Book III v2.02](https://powerpc.dev/general/PPC_Vers202_Book3_public.pdf); `rfid` encoding and behavior are cross-checked against IBM's [instruction reference](https://www.ibm.com/docs/en/aix/7.3.0?topic=set-rfid-return-from-interrupt-double-word-instruction).

## Integer compare and branch references

The `cmp`/`cmpl` and `cmpi`/`cmpli` implementations follow the architecture's signed/unsigned comparison, L-width, selected-CR-field, and XER summary-overflow behavior. `addc`/`adde` and `addic` forms update XER.CA; `addme` and `addze` add XER.CA as the carry-in, with `addme` also including minus one. `subfc`/`subfe`/`subfic` set CA to the subtraction carry-out (1 means no borrow), while ordinary `subf` leaves CA unchanged. `subfze` adds the one's complement of RA and the carry bit; `subfme` adds the one's complement of RA, the carry bit and all ones. Both extended subtraction forms update CA on every form. OE forms update XER.OV and sticky XER.SO. Immediate `b`/`bc` instructions support relative and absolute targets; `bclr`/`bcctr` apply the decoded BO condition and use aligned LR/CTR targets. Unsupported BO/BH encodings and invalid `bcctr` counter-decrement forms fault explicitly.

The register logical operations use full 64-bit GPR values and update CR0 only in record forms. `slw`/`srw` operate on the low word and zero-extend their result; `sraw` sign-extends the low-word result and updates XER.CA when a negative value loses one bits. `rlwinm` rotates the low word, uses PowerPC's MSB-numbered inclusive mask endpoints and zero-extends the masked word.

`srawi` uses the instruction's five-bit immediate shift count, sign-extends the shifted low word to the 64-bit GPR, and sets XER.CA when a negative source shifts out any one bits. Rc updates CR0, and a zero shift clears CA.

The PPC64 `sld`/`srd` operations use RB's low seven bits as the shift count and return zero for counts 64–127. `srad` uses arithmetic sign fill; XER.CA is set for negative sources when any one bits are shifted out, and for counts 64–127 it follows the sign bit. Immediate `sradi` reconstructs SH from its split encoding, arithmetic-shifts by 0–63, sets XER.CA only when a negative source loses one bits, and clears CA for a zero shift. Rc updates CR0. Unsupported shift instructions remain explicit decode faults.

`cntlzw` counts leading zero bits in the source register's low word, while `cntlzd` counts across the full doubleword. Both return 32 or 64 respectively for a zero source, may update CR0 when Rc is set, and leave XER unchanged. Their reserved RB field is checked by the decoder.

The immediate logical forms use unsigned 16-bit constants: `ori`/`xori`/`andi.` use the low half, while their shifted forms place the immediate in bits 16–31. `andi.` and `andis.` always update CR0 and leave XER unchanged; `ori`, `oris`, `xori`, and `xoris` leave condition and exception state unchanged. The initial multiply subset implements PPC64 `mulli` low-doubleword multiplication, `mullw` low-word multiplication, and signed `mulld` low-doubleword multiplication. `mullw` defines only its low 32-bit result in 64-bit mode, so this interpreter deterministically clears the undefined upper 32 bits. Its OE overflow check uses signed 32-bit representability and Rc compares the signed low-word result. `mulld` supports Rc and OE; overflow updates OV and sticky SO, and Rc records the result in CR0. The `neg` instruction computes the two's-complement negation over the full GPR width; `nego` sets or clears XER.OV when OE is enabled, preserves sticky SO and CA, and detects the signed minimum input without host signed overflow. Rc records the result in CR0.

The integer divide subset implements signed and unsigned word and doubleword forms (`divw`, `divwu`, `divd`, `divdu`), with OE/Rc behavior, sticky XER.SO, OV updates only when OE is set, and CR0 recording. Word division reads the low 32-bit operands and defines only the low 32 bits of the quotient; this implementation clears the ISA-undefined upper destination bits for deterministic tests. The ISA also leaves the result undefined for divide-by-zero and signed-minimum divided by -1. The interpreter chooses zero for such a result, and sets OV when OE is set; this is a documented deterministic policy for undefined outcomes, not a claim that hardware returns zero. Signed C++ division is guarded against those cases to avoid host-language undefined behavior.

The word multiply-high instructions `mulhw` and `mulhwu` compute the high 32 bits of the signed or unsigned 32-bit product. The doubleword forms `mulhd` and `mulhdu` compute the high 64 bits of the signed or unsigned 64-bit product. Their Rc forms compare the result as signed and copy XER.SO to CR0; these instructions do not modify XER. As with other word-result operations, the upper destination half for the word forms is architecturally undefined in PPC64 and is cleared deterministically here. The 64-bit high products are assembled from 32-bit limbs so the implementation remains portable C++20 and does not depend on compiler-specific 128-bit integers.

The initial Xenos frontend component parses the big-endian PM4 packet envelope. It exposes sequential or repeated type-0 register writes, both type-1 register indexes, type-2 no-ops, and type-3 opcode, predicate and payload bounds. A separate application routine applies type-0/type-1 writes plus the type-3 `SET_CONSTANT`, `SET_CONSTANT2` and `SET_SHADER_CONSTANTS` upload formats to a caller-sized register span; it validates packet metadata, complete stream coverage, every payload and the full write set before changing state. PM4 NOP is accepted. Unimplemented type-3 opcodes and predicated uploads fail explicitly; predicate execution needs bin-selection state, which is not modeled. `SET_CONSTANT` maps ALU, fetch, boolean, loop and direct-register spaces into the current flat register span; those areas remain provisional until checked against an authoritative Xenos register reference. Draw commands, other Xenos register semantics, shader translation and Vulkan rendering are not implemented.

Packet header and upload-field references were cross-checked against the public Xenia format/command-processor sources; this implementation contains no copied Xenia code: [Xenos packet opcode definitions](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/xenos.h) and [Xenia command processor](https://github.com/xenia-project/xenia/blob/master/src/xenia/gpu/command_processor.cc).

The data subset includes D-form accesses plus indexed `lbzx`, `lhzx`, `lhax`, `lwzx`, `ldx`, `stbx`, `sthx`, `stwx`, and `stdx`; indexed update forms `lbzux`, `lhzux`, `lhaux`, `lwzux`, `ldux`, `stbux`, `sthux`, `stwux`, and `stdux`; byte-reversed `lhbrx`, `lwbrx`, `sthbrx`, and `stwbrx`; D-form `lmw`/`stmw`; and DS-form `ld`/`ldu`/`std`/`stdu`. DS displacement is a signed 14-bit quantity scaled by four; the unsupported `lwa` DS form is diagnosed. Indexed effective addresses add GPR RA and RB, treating RA=0 as a zero base for non-update forms. Update forms reject RA=0; update loads also reject RT=RA. `lmw`/`stmw` transfer GPR RT through GPR 31 as aligned, big-endian words. `lmw` rejects base/destination overlap forms whose result is architecturally undefined. For a failing multiword access, this flat-memory prototype prevalidates the entire range; `lmw` stages loaded values before changing registers. Byte accesses may use any address; wider accesses require natural alignment in this prototype. Byte-reversed forms reverse bytes within a naturally aligned halfword or word. Loads zero-extend except for `lha`/`lhau`/`lhax`/`lhaux`, which sign-extend to the 64-bit GPR. D-form and indexed update loads/stores change RA only after successful access. Guest address mapping, permissions, MMIO and the Xbox 360 memory model remain outside this flat buffer.
